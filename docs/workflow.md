# 研发工作流设计

适用于软件开发、研究、系统建设和技术材料交付。整个流程围绕三个问题展开：近期要交付什么，怎样用最少的工作得到它，凭什么判断它已经完成。新方案先经简化再拆票，已按执行方案建立的任务可直接领取。

## 谁决定，成果存在哪里

使用者确定目标、优先级和影响交付的取舍。技术负责人维护路线与方案，工程师执行任务并保存原始证据，项目经理根据已确认的变化维护团队的任务安排。Agent 在授权范围内调查、起草、执行和核查。每次迭代细化近期成果，远期只记录方向和重新评估的条件。

| 记录位置 | 维护内容 |
| --- | --- |
| Notion 项目主页 | 团队共用一个正式入口。方案写入原生正文，Issues 和里程碑记录执行安排与结果。 |
| 项目目录、版本库、实验环境 | 代码、数据、模型、实验记录和交付文件保留在原位置。方案与任务链接到对应版本和证据。 |
| 工程项目的 issue tracker | wayfinder 的决策地图、triage 等按目标项目的配置工作；可选 GitHub、GitLab 或本地 Markdown。 |
| 其他团队记录 | 项目经理按团队约定人工维护，例如语雀。研究资料与工程软件由当前任务和可用工具决定。 |

## 每一步如何交接

| 环节 | 输入与工作 | 交给下一步 |
| --- | --- | --- |
| 讨论澄清 | 用 grill-with-docs 处理一般需求。grilling 在一轮中只问当前能回答的问题，domain-modeling 记录已解决的术语与持久决定。跨会话、依赖复杂时可选 wayfinder，先建图，再逐次解决决策子 Issue。 | 目标、约束、关键取舍、待验证的问题。 |
| 项目初始化 | 首次组织 Notion 项目时，init-notion-project 在指定父页下建立或复用主页。已有内容与人工布局保留。 | 一个正式项目入口。任务和里程碑区域先占位。 |
| 形成方案 | to-notion 读取已有讨论和证据，补足会改变目标、路线或验收的缺口。研究任务明确基线、对照与测量条件。 | 同一方案页上的候选范围、依据、预期行为和验收条件。 |
| 简化 | simplify 检查需求来源，比较取消、复用、缩小或延后。把转移给人工、协作者和后续维护的成本算进去。 | 在原页确定本轮执行方案及验收条件。无需再删也可定稿。关键取舍待定时只交建议。 |
| 组织执行 | to-pm 核对当前版本的 simplify 定稿结论，按近期成果拆分工作，区分真正阻止开工的依赖和可以并行的准备。首次需要时建立或复用两个数据库。 | 可领取的 Issue 和可勾选的 ticket，列明输入、动作、交付证据、牵头工种与真正的阻塞。远期先留里程碑。 |
| 执行与验收 | 软件用 implement，明确实现整个 Issue 还是其中一个 ticket，以及需审查的提交和未提交改动。调查用 research，正式材料用 project-docs，现场工作由相应人员执行。 | 实现和测试、研究记录、现场结果或经检查的文件；记录证据、适用条件及剩余差距。 |

主流程中的显式入口由用户点名或明确提出相应任务。用户一次授权多个环节时，按顺序完成，实质取舍由人决定。入口内部可以调用其配套支撑技能。例如 implement 调用 tdd 和 code-review；research 也可供其他环节补证。各入口的调用配置随[项目内源码](../skills/)提供。

简化之后，先依据执行反馈改进方法，再考虑加速；稳定且重复的操作才值得自动化。软件看约定行为和测试，研究看证据是否足以作出判断，系统看约定环境下的实际能力，正式材料看内容和最终呈现。

## 团队从主页看到什么

1. **Issues** 排在首页最前。第一视图按 Backlog、Todo、In Progress、Done、Canceled 展示并保留空分组。第二视图按工种展示待推进工作。
2. **里程碑** 记录阶段、核心交付与当前情况。阶段页包含目标、完成条件及关联任务视图，筛选首页同一任务源。
3. **项目文档** 按实际用途整理方案与决定、技术与接口、验证与成果。常用文档从主页可达。
4. **过程与归档** 保留历史决定、阶段记录和必要的数据源入口。

Issue 采用稳定编号。单项 ticket 默认是 Issue 内的执行步骤，有独立责任、排期、依赖或验收需要时再拆出。wayfinder 的决策子 Issue 独立跟踪一个决定，遵循所选 tracker 的约定。术语和数据库布局分别见[术语表](../GLOSSARY.md)与[Notion 项目约定](../skills/_shared/notion-project.md)。

## 结果如何回到方案

执行者把结果与证据交回原 Issue。to-pm 只更新实际完成的步骤，项目经理按整体条件确认 Issue 与阶段状态。例如会议待办的录入功能通过测试，而成员查看权限仍待验证时，录入步骤可勾选，Issue 保持进行中。

新证据改变范围、路线或验收时，由 to-notion 在原页单列候选变更，保留现行执行版。simplify 定下修订范围后，to-pm 才调整对应任务与依赖。仅补证据或改字沿用原定稿。重复调用前读取人工修改；写入中断先查哪些操作已经成功，再补缺项。各技能共用[记录写入约定](../skills/_shared/record-writing.md)。

五项自建技能的具体输入、完成判据和验收场景见[自建技能设计与验收](custom-skill-design.md)。首次试用可按[会议待办示例](../examples/meeting-actions.md)走通方案、任务和反馈。
