# 自建技能设计与验收

本页以 2026-10-30 的工作流为起点，记录五项自建技能当前的设计依据和验收场景。全部技能在流程中的位置见[工作流设计](workflow.md)。

## 共同约定

**方法与能力分开。** 技能定义如何判断和推进工作，Notion 连接器及本地工具负责操作。根据当前工具实际能力执行，页面 ID、项目 ID、负责人、状态与字段从用户或系统读取，不写死某个账户的配置。

**个人技能都是显式入口。** 用户点名或明确要求执行该流程后启动。每项包含 `SKILL.md`，前置元数据写明名称与简短用途；Codex 的 `agents/openai.yaml` 设置 `policy.allow_implicit_invocation: false`。正文保留主要步骤和完成条件，较长的条件性规则放入按需读取的参考文件。一个入口可以调用适用的辅助技能；另一个显式入口由用户选择，不能仅因出现在流程图中就自动启动。

**保存位置是交付的一部分。** 写入前告知目标名称、链接和操作，完成后返回实际入口。目标不明时先查项目约定，再请用户指定；同时继续准备内容。已有明确位置和授权时直接执行，位置提醒不增加重复确认。草案、已保存和部分成功应明确区分。

**更新沿用原记录。** 修改前读取最新内容，保留人工编辑、有效依据、关联关系和范围外内容。发生并发冲突时重读并合并，实质决定冲突交由用户取舍。批量操作保存成功项；超时或结果不明时先回读，确认未发生再重试。无法确认或相同错误持续出现时停止重试，说明已完成部分与缺口。分享权限、向他人发送消息和团队承诺分别按对应授权处理；语雀由项目经理人工维护。

**按需要组织依赖。** 同时生成多项技能时，可将上述记录操作放入普通共享参考文件，各入口明确何时读取。单独生成一项时，将所需规则放入该技能的正文或参考目录，使其能独立安装。需要文档、表格、演示文稿、PDF 或研究能力时，调用当前可用的对应技能；没有技能调用工具时读取其说明并执行，能力不可用时说明具体缺口。

**用行为检验设计。** 除名称、元数据与引用检查外，使用下列场景观察是否作出正确取舍。离线草案验证、真实系统写入和文件渲染分别记录，不能用一种检查替代另一种。

## `to-notion`：将已有共识形成可维护方案

**设计意图。** 借鉴 Matt `to-spec` 的“综合已有讨论”方法，结合内部研发方案写作。保留需求、技术取舍与验收设计，把正式方案保存位置改为 Notion 原生正文。它应减少从讨论到方案的信息损失，避免再次启动完整访谈，也避免同时维护 Markdown、HTML 和 Notion 三份正文。

**输入与产出。** 输入是已有讨论、明确决定、当前方案及相关证据，适用于需求或建设方案、研究规划、技术决策和阶段结论。产出是指定 Notion 页面中的原生正文，或用户要求的未发布草案。代码、数据和实验记录保留原位置，方案用链接引用；本地导出只在需要时提供，并注明来源。

**执行过程：**

1. 读取讨论、现有方案和证据。软件工作核查相关实现、测试接口、领域术语和 ADR；研究与系统工作核查已有结果、资源与验证条件。
2. 读取项目主页的文档分类，优先更新原文档；新增常用文档按用途在主页直接展示入口，少量文档不增加中间目录。定位并告知“项目主页 → 目标页面”及链接，说明更新正文还是新增子页。用户已经给出唯一目标页时，无需为补齐主页层级再次询问。目标未定则继续整理草案，写入等待位置明确。
3. 沿用已确认的决定直接综合。只有会改变目标、路线或验收的缺口才集中提问；待验证假设明确保留。已完成的讨论不因套用模板而重新开始。
4. 按文档用途选择内容。需求方案写问题、采用路线、范围、用户行为与完成条件；研究规划写问题、依据、候选解释、基线、条件及判断方式；技术决策写选项、理由与重审条件；结果记录写实际成果、证据、适用范围及剩余差距。
5. 软件方案覆盖本轮用户场景、关键失败行为、必要接口和数据约定。测试优先沿用已有、较高层且尽量少的接口，验证外部行为并记录测试先例；新增或改变已认可的测试边界时请用户确认。研究方案保留对照、测量与评价条件，缺乏依据的数值仍列为待定。
6. 正文呈现决定和依据，重要主张附近给出来源，区分目标、建议与实测结果。易过期的文件清单和实现细节留在执行材料；原型中的状态机、类型或结构比文字更准确时，保留必要片段。
7. 按共同约定保存并回读，检查正文、关键条件、引用及页面关系。数据库记录使用实际字段结构。实质变化在原页标为待简化，保留现行执行版与关联记录。只有经 simplify 定稿的变化才交给 toPM 重排。

**完成判据。** 本轮范围与完成条件已表达，关键未知项可见，接手者能据此开展下一步。保存任务还需回读成功；交付页面名称与链接、主要变化和未完成项。草案明确“尚未写入 Notion”，正文完成不等于研究或实现已完成。

**重建后的验收示例：**

| 场景 | 应有行为 |
| --- | --- |
| 用户提供已有执行页，提出新增验收条件 | 读取原文、保留现行范围和人工备注，把影响执行的变化记在同页待简化，回读核对 |
| 用户只要研究方案草案，尚未选 Notion 页面 | 先交付草案并说明未保存，页面位置不阻塞写作 |
| 材料写有“仿真成功率 90%”，尚无实机证据 | 保留仿真条件与实机验证缺口，不改写成实机效果或交付承诺 |

## `simplify`：减少达成目标所需的工作

**设计意图。** 把“先质疑需求，再删除简化”落实为方案审查，在 `to-notion` 的候选方案与 `to-pm` 的执行拆解之间确定本轮执行方案。借鉴 Matt 的删除测试：删掉某个部分后，复杂度是真的消失，还是转移到其他模块、人工操作或协作者身上？它审查工作是否值得做，不以减少文字、代码行数或 issue 数量作为成功标准。

**输入与产出。** 输入是具体方案、需求来源、完成判据、已有能力和执行进度。产出是保留、删除、复用、缩小或延后的取舍及依据；获授权的改动回写原方案。仅要求审查时交付建议。原方案已经足够简单时，可用「无需再删」及依据完成定稿。

**执行过程：**

1. 明确本轮成果和判断方式，区分真正的需求、实现需求的做法与未经验证的假设。追溯关键要求为何存在、由谁提出。对目标也可提出重审理由，但改变价值、指标或交付承诺由用户决定。
2. 先审视整个方案，再检查主要组成，依次考虑不做、复用、缩小或延后，最后简化保留项。每项关键变化说明节省了什么、损失或代价是什么、依据在哪里；延后项注明重新考虑的条件。
3. 比较整体成本，包括运行、维护、协作、迁移、取消进行中工作及恢复删减项的代价。已投入成本本身不是继续投入的理由，未来可能有用也不足以证明现在需要建设。
4. 沿依赖检查删减后的完整成果。软件保留关键行为、故障处理和数据约束；研究保留基线、对照和测量；材料保留读者决策所需依据。缩减样本或场景改变结论适用范围时，应作为实质取舍说明。
5. 证据足够时直接采用；无法判断能否删除时，提出能区分方案的最小检查。无需为每项细节建表、设置删减比例，或额外启动一轮研究。
6. 先呈现实质取舍，再按授权修改。未决定的建议与已采纳变化分开记录；修改 Notion 时按共同约定告知位置、保留进度并回读。已有任务不因一条建议自动取消。

**完成判据。** 主要工作都有保留或删减依据，关键依赖和评价能力仍成立，在原页可定位经简化定稿的具体范围和验收依据。交付修订入口或审查建议、实际减少的工作、剩余决定及回写状态。优化、提速和自动化留给保留工作中的实际瓶颈与稳定重复需求，不为凑齐五步新增任务。

**重建后的验收示例：**

| 场景 | 应有行为 |
| --- | --- |
| 离线导出功能的方案同时加入账号、云端队列和统计面板 | 检查它们是否支撑当前成果，删除无依据的建设，保留导出与必要验证 |
| 研究方案提议删除对照组，以缩短时间 | 检查是否仍能回答研究问题；若结论降级，应说明并交由用户取舍 |
| 一个明确的小修改已经具备直接实现路径 | 可以得出“无需进一步简化”，不添加阶段、仪表盘或自动化任务 |

## `to-pm`（toPM）：组织并维护执行

**设计意图。** 继承 to-linear 的成果拆分、内部 tickets、真实依赖与范围核对方法，以 Notion 统一承载任务和里程碑。新建或按新版重排任务时，输入是经 simplify 定稿的执行方案。输出是可直接领取的 Issue 和 ticket。已有任务的进展反馈及里程碑复盘可按原记录单独处理。读取共同约定与 `skills/_shared/notion-project.md`。

**执行过程：**

1. 区分首次拆解、方案调整、进展回写和阶段复盘；读取源方案、相关任务全文及必要评论，保留已有进度。
2. 定位项目主页、数据库和 schema。首次需要执行安排时建立 Issues 与 Milestones 并替换预留位置；重复调用复用现有对象。缺少项目入口先查约定，初始化仍是独立入口。
3. 按成果与项目工种拆分，ticket 使用正文清单，独立排期、责任、依赖或验收有需要时再提升为 Issue。近期票写明输入、动作和验收证据。只有方向的远期工作只立里程碑并记录细化条件。保留软件完整行为切片、研究证据判据、系统实验条件和材料检查要求。
4. 稳定编号、按工种分工、五状态为共同约定。新项目编号默认项目标识加连续序号，保留旧编号且不复用取消编号；人员、日期、优先级按需填写。只将真正阻止开始的前提连接为阻塞依赖，检查循环。
5. Issues 第一视图五状态，第二工种；Milestones 主表显示阶段、核心交付和当前情况。阶段页展开一句目标、简短完成标准和自身任务视图，依据按需折叠。文档直接分类展示，避免多层目录。
6. 回写定位原编号，保留人工编辑、成果与历史。ticket 完成只更新步骤，Issue 完成依据整体验收；阶段结论依据真实能力，任务数量仅为统计。影响路线的结果指出需修订的方案。
7. 已授权工作直接写入并核对真实关系，部分失败只补缺项。草案不写入，建票不启动实现，不自动分享或发送消息。

**完成判据。** 范围覆盖、编号唯一、工种与五状态正确、依赖可执行；首页与阶段共用任务源，阶段过滤正确；返回实际入口与未完成事项。

| 验收场景 | 应有行为 |
| --- | --- |
| 只有刚归档的候选方案，或新版范围与上次简化结论不同 | 暂停相应拆票，指出需完成简化的范围；已授权连续推进时先完成 simplify |
| 已有简化定稿，首次组织执行 | 复用或建立两个数据库，交付能开工的 Issue 和 ticket；重复调用保留原记录及视图 |
| 多工种协作且设备尚未到货 | 明确牵头工种与局部等待，资料和模型准备可并行 |
| 一项 ticket 完成，整体仍待真机验证 | 仅更新步骤与结果，保留 Issue 未完成状态 |
| 方案变化及部分创建超时 | 保留原编号和成果，查证成功项，仅补缺项 |

## `project-docs`：将方案和证据转为正式材料

**设计意图。** 将 `formal-project-docs` 的正式写作、证据处理和文件审校合并到 `project-docs` 一个入口，以读者要理解或决定的事情组织内容，并复用各文件技能完成制作和检查。它没有 Matt 的同名原版；借鉴的是职责清晰、步骤有完成条件、细节按需加载的设计原则。内部持续维护的方案由 `to-notion` 承载，正式方案、报告、汇报和预算由本技能交付。

**输入与产出。** 输入包括已确认的方案、原始证据、现有文档、用户模板及受众和格式要求。产出是所需的正式文档、演示文稿或预算文件，附明确路径或目标链接及影响使用的未决事项。仅制作用户需要的格式，Markdown 本身可以成为交付物。

**执行过程：**

1. 区分事实来源、内部记录和风格模板，明确读者、用途、必要内容、格式与篇幅。读取已有决定并沿用交付目录，告知保存路径；只对会改变内容或承诺的缺口集中提问。
2. 关键主张回溯证据，预算核对数量、单价、单位及估算口径。冲突按原始证据和已确认决定处理，不凭文件修改时间判定事实。需要外部补证时调用 `research`，缺口仍存在则如实保留。
3. 优先遵循用户指定结构。项目方案说明对象、需求、路线、阶段成果和投入；结果报告说明条件、方法、结果及适用范围；汇报聚焦本次决定；预算呈现输入、计算关系和估算依据。成熟内容直接制作，结构存在实质取舍时先给可审阅提纲。
4. 使用连贯、自然的正式文字正面描述方案。表格用于比较或数据，列表用于步骤或并列项。删去内部过程话术、重复摘要与装饰性信息；目标、估算、实测结果及必要不确定性仍清楚可辨。
5. 技术主张保留对象、条件、方法、证据和适用范围。现场照片使用真实原始材料，示意图明确标识。多份交付共用一套事实；排版阶段改变数字或结论时同步相关材料。
6. 按格式调用当前可用的 Word、演示文稿、表格或 PDF 技能。遵循用户模板，保留需要继续编辑的图表和数据，预算用可检查公式计算。原材料、内部处理记录和正式成果分开存放。
7. 先检查内容，再检查呈现。内容检查覆盖主张依据、数字、单位、范围与跨材料一致性；Word／PDF 逐页渲染，演示文稿逐页查看，工作簿重算并用代表性输入变化检查公式及版面。Markdown 检查结构、链接和阅读方式，无需为检查再生成另一种文件。
8. 修正问题并复查受影响部分，返回实际文件入口。工具限制导致未检查的部分写明具体影响；制作不自动授权发送、发布或扩大分享范围。

**完成判据。** 内容回答了读者的问题，重要结论和金额有依据，各交付物事实一致，所需格式已生成且相应检查完成。未检查版本不能称为通过；不确定性用正式条件表达，不能在润色过程中被删除。

**重建后的验收示例：**

| 场景 | 应有行为 |
| --- | --- |
| 对外报告的素材含内部试验号、未定义缩写、私有链接 | 正文说明可披露的试验对象、条件、结果和限制，内部线索仅供内部核查；外部读者可独立读懂 |
| 将初步研究整理为技术评审简报 | 区分事实与建议，保留测试条件和证据缺口，去掉内部讨论过程 |
| 同时制作方案与预算，设备数量在制作中变化 | 同步正文、表格和合计，重算并复查相关交付物 |
| 用户只要 Markdown 报告，或当前无法渲染 Word | 前者完成 Markdown 检查即可；后者说明 Word 呈现尚未验证，不声称已通过版面检查 |

## `init-notion-project`：建立项目框架

**输入与产出（2026-11-07 修订）。** 用户给出已有主页时直接复用。新项目先用用户指定的父页，其次用当前业务项目明确约定的父页，两者都没有时再询问。以项目名称和已有标识核实主页，返回实际链接。「项目总览」是维护团队在业务项目中采用的约定。

**执行过程。** 读取现有页面及共享记录规则，按 Issues、里程碑、项目文档、记录与归档建立布局。前两区仅保留简短占位，数据库由后续 toPM 创建；文档按已有内容分类，无内容时保留区域，不建空子页。已有数据库、文档和人工布局保留，重复调用只补缺项。返回实际主页，后续由用户调用 to-notion。

**完成判据。** 父级和项目身份正确，原内容保留，框架简洁，无提前建库或重复页面；完成结构核对并说明实际保存状态。

| 验收场景 | 应有行为 |
| --- | --- |
| 新项目无文档或任务 | 建主页与占位，不建数据库、任务或空分类子页 |
| 用户指定的父页与业务项目约定不同 | 直接采用用户指定的位置 |
| 用户未指定，业务项目明确约定了父页 | 沿用项目约定。遇到无法区分的同名候选时请用户指明 |
| 用户和业务项目都没有指定父页 | 询问应放在哪个父页，名称或现成链接均可，等待时可准备草案 |
| 已有主页包含任务库与人工说明 | 只补缺框架，保留数据库、关系与人工内容 |
