# Simplify

对已有方案做**删除测试**，通常位于 `to-notion` 与 `to-pm` 之间。目标是减少达到本轮成果所需的工作；方案已经足够简单也是有效结论。

## 1. 明确成果与必要条件

读取最新方案、需求来源、已有能力和执行进度，明确本轮成果及完成判据。区分需求、满足需求的做法与尚无依据的假设。追问关键要求为何存在、由谁提出；改变目标或交付承诺的建议交由用户取舍。

## 2. 删除测试

先看整个方案，再看其主要组成，依次考虑：

- **不做：**取消后损失哪个具体结果？没有实质损失时提出删除。
- **复用：**已有能力、方法、数据或人工步骤能否满足需求？计入运行、维护及他人的协作负担。
- **缩小或延后：**减少场景、选项和阶段能否仍达到本轮成果？延后项写明重新考虑的条件。
- **简化保留项：**合并重复工作、记录或接口。删除后复杂度若转移到调用方或人工操作，应比较整体代价。

对关键变化说明节省、代价与依据，每个主要保留项说明其必要性。无需为每个细节建表，也不设置删减比例。

## 3. 验证删减成立

沿依赖核对完整成果与评价能力：软件保留关键行为、故障处理和数据约束；研究保留支撑判断的基线、对照及测量；材料保留读者决策所需依据。缩减样本或场景导致结论适用范围变化时明确说明。

不确定时提出能区分方案的最小检查，已有证据足够则直接采用。计入迁移、取消进行中工作和恢复删减项的代价；已花费的成本本身不构成继续投入的理由。

## 4. 呈现取舍并回写

给出简短的保留、删除、缩小或延后建议及代价。已有授权内可逆修改直接完成；重大取舍等待用户决定，审查请求交付建议。

回写前读取 [记录写入](../_shared/record-writing.md) 中相关平台的规则，告知目标位置。确定的变化回写同一份方案；已有执行工作受影响时说明影响，按对应授权调整。未决定的建议与已采纳改动分开表达。

完成时，主要工作有保留或删减依据，依赖与评价方式仍成立。交付修订入口或审查建议、实际减少的工作和剩余决定，明确是否已回写。

五步法在此落实为质疑需求、删除简化。保留工作中的优化、提速与自动化应由实际瓶颈和稳定重复需求驱动。
