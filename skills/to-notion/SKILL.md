# 编写与更新项目方案

把已讨论的需求和证据写成可供 `simplify` 审查的候选方案。团队在 Notion 原页维护方案，也可单独记录实验结果或技术决定。代码、数据和实验日志引用原位置。

## 执行流程

1. **找到本次要写的内容。** 读取讨论、原方案与相关证据。更新指定页时，先按 [Notion MCP 约定](../_shared/record-writing.md#notion)核实访问能力并读取原文，找到要改的段落和应保留的人工记录。需要新增页面时，查[项目主页](../_shared/notion-project.md#主页)已有分类和同用途文档。只要草案且已有材料足够，直接起草。
2. **综合已定事项。** 按下表选取正文内容。把已确认的取舍写成决定，把尚待验证的判断写成假设。只有缺口会改变目标、路线或验收时才请人决定。局部更新保留原页其余内容。新证据改变结论时修订原段并注明依据，重复提交同一结果时复用已保存的正文。
3. **核对证据和验收。** 关键主张就近标明来源。软件方案结合现有实现、领域术语、ADR 与测试先例，覆盖本轮用户场景、失败行为和必要的数据约定。优先通过已有高层接口观察结果，新增或改变测试边界时请用户确认。原型中的状态机或类型若比文字准确，可保留必要片段。
4. **归档并交接。** 按[方案存档](../_shared/notion-project.md#方案存档)区分候选范围、现行执行版和证据记录。已有执行版时，把范围、路线或验收的实质变更单列待简化，保留现行正文和原票关系。交代本次拟做范围、验收和待取舍项，供 `simplify` 接手。保存时按[记录写入约定](../_shared/record-writing.md#通用规则)告知位置并回读，返回实际入口。只交草案或权限不足时交付正文并注明尚未写入。

## 按用途选内容

| 这次要形成什么 | 接手者需要读到什么 |
| --- | --- |
| 需求或建设方案 | 谁遇到什么问题，本轮覆盖哪些场景、哪些留待以后，怎样观察到交付成功 |
| 研究计划 | 研究问题、已有证据与候选解释，基线、对照、测量条件，以及用什么结果判断 |
| 技术决策 | 考虑过的选项、采用理由、成立条件，以及何时重审 |
| 阶段或实验结论 | 实际结果、证据来源、适用范围，以及离交付还差哪项验证 |

例如，记录显示「控制器在仿真中通过 27/30 次」，而验收要求实机运行，原页应同时保留仿真条件和未完成的实机验证。导出本地副本时按需注明源页。
