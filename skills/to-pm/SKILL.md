# 把执行方案拆成可领取的工作（toPM）

主要交付是**可以直接开工的 Issue 和 ticket**。Issue 承担一项可独立验收的成果，ticket 是其中可勾选的具体动作。Notion 里程碑把这些成果组织到阶段中。

## 执行流程

1. **核对执行依据。** 首次拆票或按新方案重排前，找到 `simplify` 对**当前范围**的定稿结论和对应的验收条件，按[方案存档约定](../_shared/notion-project.md#方案存档)核对版本。旧项目已有可核实的等价记录可直接用。只有候选方案、过期结论或待决定的建议时，指明哪部分需先简化，暂停该范围的拆票，包括票据草案。用户针对整份新版要求拆票时，指出版本差异。已一并委托简化时先完成简化再拆票；仅在明确交办旧版有效范围时单独安排该部分。实际访问 Notion 前核实 [MCP 与页面权限](../_shared/record-writing.md#notion)。
2. **从验收条件反推 Issue。** 按[拆解与调整](references/planning.md)为每项近期成果写明执行来源、交付物、牵头工种及可观察的验收条件。同一成果复用已有编号。远期只有阶段意图时，记在里程碑并写明何时细化。
3. **让接手者能做第一步。** 在每个近期 Issue 内把工作写成可勾选的 ticket，交代用什么输入、做哪个动作、留下什么结果或证据。注明真正阻止开工的前提。按项目现状指出现在可领取哪一项；全部受阻时指出解除阻塞的具体条件。检查本轮保留的验收条件均有对应工作，删去或延后的范围不混入近期票。
4. **交付并核对。** 请求草案时直接给出拆分。获授权写入时按[记录写入约定](../_shared/record-writing.md#通用规则)复用或补齐库、记录与关系，回读 Issue、ticket 和受影响视图，交付实际入口及未完成项。超时先查已保存项。建票完成后即可按票领取；实际实施按用户交办范围推进。

## 已有任务如何维护

- **新执行方案改变了工作**，按上述流程只调整受影响的原票，保留已做的步骤、证据和人工备注。
- **用户只报告进展、调整既有分工，或要求复盘**，直接定位原 Issue 或里程碑，按[进展与复盘](references/progress.md)局部更新。此类维护沿用原有依据；若反馈引出范围、路线或验收变更，另记入原方案，待该变更经过简化再重排。

例如，「现场测量完成，原始数据已上传」可以勾选测量 ticket。若整项还要求误差复核，交接时应指出待做的复核动作及其判据。
