# toPM

将明确、按需要简化的方案组织为可接手的执行安排，并按反馈持续维护。Notion 项目主页是团队入口，方案正文保留依据，数据库跟踪阶段和任务；代码、数据与实验记录引用原位置。技术名使用 `to-pm`，用户称呼为 toPM。

## 1. 读取来源与确定本次动作

读取当前方案、相关 Issues 全文、必要评论、已有进度及里程碑；按需核查实现、术语、ADR、测试或实验条件。区分首次拆解、方案调整、执行回写、阶段复盘。草案请求只交付草案。

读取 [记录写入](../_shared/record-writing.md) 与 [Notion 项目布局](../_shared/notion-project.md)。定位并告知项目主页和实际数据库。缺少主页时先查项目约定；初始化是独立入口，不擅自另建项目。已有明确授权继续，影响目标或团队承诺的未决取舍集中提出。

## 2. 首次建立执行载体

仅在需要持久化执行安排时创建或复用 Issues 与 Milestones 数据库，并替换主页对应占位。先读取真实 schema、关系、工具格式和能力，再按共享布局建立最小字段及视图。不创建重复任务库或按工种分开的数据副本。

先建立真实记录，再关联里程碑、任务和依赖。主页 Issues 默认第一视图为五状态看板，第二为工种；里程碑使用阶段、核心交付、当前情况的简洁总览。每个里程碑内嵌仅筛选自身任务的视图。

## 3. 按成果与工种组织

Issue 对应独立跟踪的成果，ticket 默认是其中的执行清单。按项目实际工种确定牵头职责；有独立负责人、排期、依赖或验收需要时再拆 Issue。工种与人员分别记录，未知人员留空。

- 软件优先贯穿必要层次、可独立验证的完整行为。必要前置重构先行；大规模迁移采用兼容扩展、分批迁移、移除旧路径，说明共同集成条件。
- 研究以问题、比较条件与证据为成果，假设不成立也可完成研究任务。系统验证说明设备、数据、环境与人工前提；材料说明受众、格式与检查要求。
- 近期细化到可接手，远期保留方向与细化条件。路线未定时，近期任务取得决策所需证据。

每项用简短正文说明成果、来源、完成条件、tickets 与确有必要的前提，按实际内容选用标题，避免空模板。详细设计链接回方案。

只把真正阻止开始的前提建立为阻塞关系；局部步骤等待写在 ticket 附近。检查循环依赖、外部前提及承接方。核对每项已确认完成条件都有任务承接，复用现有记录并保留进度。

## 4. 维护执行与阶段结论

依据稳定编号、内容和来源定位原记录，先比较变化再更新。重命名、换工种、调整阶段保持 Issue 编号；新编号遵循项目约定，未约定时使用项目标识加连续序号，查重后分配。不要复用已取消编号。并发分配无原子保证时串行建项并复核冲突。

沿用五个状态：Backlog、Todo、In Progress、Done、Canceled。新工作默认 Backlog；已明确纳入近期安排可用 Todo；开始、完成与取消依据实际反馈和授权，不因创建或拆解自动推进。ticket 完成只更新该步骤，Issue 完成依据整体成果与验收。

方案调整保留已完成成果、人工备注和结果；实质范围取舍待明确后再调整活动任务。重要结论影响路线时指出需要 to-notion 更新的方案，不自动启动其他显式入口。

阶段当前情况用一句有依据的描述，完成任务比例仅可作为任务统计，不代替能力验收。阶段页面默认只展开一句目标、简短完成标准与任务视图；详细依据按需折叠。复盘区分实际成果、适用范围、差距与下一步。

## 5. 写入与交付

首次拆解或重大重组需让安排可审阅；已有认可或明确授权时直接执行，不重复索要确认。先保存记录，再用真实标识连接关系；失败时保留成功项，只补缺项。

检查范围覆盖、编号唯一、五状态、工种、归属、依赖及阶段视图过滤；确认首页和阶段使用同一任务源。返回实际入口、主要变化及未完成事项。建票不启动实现，写入不授权分享或向他人发送消息。
