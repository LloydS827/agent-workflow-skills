# 创建或改进技能

由用户点名调用，例如 `$skill-builder`。用户可以带来一种做得顺手的方法、一项尚无做法的固定需求，或一个想改的技能。交付可试用的技能、调用示例和验证结果。如果已有工具就能满足需求，给出更直接的做法。

## 执行流程

1. **弄清要复用什么。** 根据用户的起点选一种做法，只追问会改变交付的取舍。
   - **已有经验。** 从一次实际工作中找出哪项判断改变了结果，换个条件时又该怎样做。
   - **只有固定需求。** 弄清谁在什么情形下使用、拿到什么才算完成，据此提出做法。需要例子时可以自行构造。
   - **已有技能。** 读现行入口和它实际引用的材料。如果技能源自一种工作方法，对照用户给的原始说明或一次真实使用，找出应保留的分工、判断和产物，再确定要改哪一步。
2. **选择合适的实现。** 先看已有技能或工具能否承接。每次需要结合材料判断、解释或调整步骤，适合做成技能。固定时间运行已有操作可用定时任务，特定事件发生时执行固定检查可用 Hook，规则确定的数据转换可用脚本，一次性的工作可以直接完成。已有工具就能满足要求时，交付相应做法，到此结束。既需自动启动又需判断时，说清什么负责启动、技能负责哪项判断。
3. **编写或修订 `SKILL.md`。** 新建时使用项目约定的技能目录，修订时在维护源改动，沿用原有调用方式。按使用者熟悉的语言写清三件事。
   - **何时用。** 文件开头的 `name` 与目录名一致。`description` 用一句话说明什么情况下用、能得到什么。
   - **怎样做。** 标题下用一小段交代从什么材料接手、把什么交给谁，再按顺序写具体动作。碰到需要判断的步骤，写明看哪条证据、不同结果各怎么做。
   - **怎样算完成。** 最后一步说明接手人如何核对交付物。某一步确实要用模板或详细资料时，在那一步链接。

   某个判断难写时，找一个处理过相似问题的技能，只参考它对应的步骤。
4. **用实际调用检验。** 给试用者请求和原始材料，预期结果留作核对。新建时可与直接对话比较，修订时给新旧版相同输入，兼测要改的行为和原本有效的用法。如果工作跨轮或会更新文件，就从相同的已有内容开始，接一次追问，再打开最终产物检查。两版都做对的记为持平；发现缺口就改对应指令并复试。交回入口路径、一句调用请求、观察到的差异和仍待验证的条件。只委托设计或草案时，交到约定阶段。

## 取舍示例

“每周五提醒我交周报”用定时提醒即可。“我写周报时，希望从工单和会议记录里区分已交付、待验证和受阻事项”适合做成技能。试用时给它一条“开发完成、尚未联调”的原始记录，看它能否把已完成的工作和仍缺的验收证据分别写清。
