# 实施整份软件方案

接手已交办的整份软件方案。先弄清项目已经能做什么、还欠哪些交付、每项工作要用到谁的成果，再安排实现。交付一个经过整体验证的集成版本，并逐票说明完成证据和剩余条件。只委托一张票或票内一步时，用 [implement](../implement/SKILL.md)。

## 执行流程

1. **核清范围和起点。** 读当前执行版、里程碑与关联原票，再查相应代码、已有提交、测试和在办工作。按稳定编号把每项验收条件对到已有成果，区分已验证、有人在办、尚待实施和本轮范围外的工作。对已标完成但缺证据的条件先复核。方案已有承诺却找不到承接票时，指出缺口，由任务负责人按项目约定补齐。团队 Notion 项目按[访问约定](../_shared/record-writing.md#notion)找到 `simplify` 定稿的范围和 `to-pm` 的原票。其他项目沿用现有规格和任务系统。记下集成起点，已有集成分支、在途提交和他人工作都要纳入判断。
2. **从成果排出顺序。** 逐票回答“开工需要什么，哪张票或哪个外部条件能提供，凭什么知道已就绪”。结合实际接口、数据格式、迁移和验收环境核对票面依赖。接口已约定、双方能独立实现和验证的 Issue 可并行。共用尚未确定的接口、排他的资源或同一段待改逻辑时，先排出交接顺序。区分阻止开工和只影响最终验收的条件。团队的票内 ticket 默认留在原 Issue，已有独立工单的项目沿用其粒度。
3. **给出首轮安排并开工。** 用原编号交代首轮安排和理由，指出哪些成果就绪后能解锁下一项。人手或环境有限时，结合里程碑优先级，先做影响后续交付的前置工作。只委托规划时交付到这里。已委托实施时，建立或复用集成分支，为就绪项分别安排从最新集成提交起步的工作分支和独立工作区，向执行者提供原票、所需输入、基点及验收接口。按约定边界使用 [tdd](../tdd/SKILL.md)。有多个执行者时并行派发，单执行者沿同一顺序推进。
4. **逐项集成并重排。** 并行执行时由负责合并的执行者逐项接入。合并前核对依赖成果和最新集成版本，处理接口或代码冲突，运行受影响的测试。将通过的变更合入同一集成分支，记录原编号、提交和证据，再重算哪些工作可开工。恢复执行时先核对已合入、在办及尚未合入的工作，避免重复派发。遇到环形依赖、缺少决策或外部输入时，继续能独立完成的部分。受阻票沿用项目已有状态选项，写清缺什么、谁能提供、何时可继续。改变范围或验收的提议交回方案负责人。
5. **按整份方案验收。** 从用户实际入口验证跨 Issue 的结果，运行项目完整检查，以集成起点为基准做[代码审查](../code-review/SKILL.md)，修正后复验。对照原方案逐项报告已验证的交付、仍缺的证据与下一步。团队项目把结果交给 `to-pm`，已交办回写时按[原票进展约定](../to-pm/references/progress.md)更新。工程任务系统沿用项目的结项与 PR 约定，需要 PR 时在首批变更集成后建草稿，在代码审查条件满足时转入正式审查。保留仍待外部验收的原票。清理本轮已合入且干净的临时工作区，保留未合入的变更供续做。

## 排序示例

导入项目中，甲票按已定格式解析文件，乙票用固定样例实现校验规则。两者可同时开始。丙票接通实际导入命令，要等两项成果集成并验证后才能验收。若客户样本尚未到，可先用合成文件跑通命令，现场兼容性继续列为待验。
